### 사이즈 가이드 · 핏 가이드를 따로 세운 이유

이 사이트의 존재 이유가 "사진이 아니라 치수로 고르게 한다" 인데,
**실측표를 공개해놓고 읽는 법이 없으면 반쪽**이다.
둘레인지 단면인지 모르면 값이 2배 차이로 읽히고, 그 오해가 그대로 교환 CS 가 된다.

### 교환·반품을 별도 화면으로 세운 이유

CLAUDE.md 가 **"교환 흐름은 부가 기능이 아니라 핵심 흐름"** 이라고 못박았다.
의류는 사이즈 교환이 CS 의 대부분이고, 운동체형 타깃이면 더 그렇다.
주문 상세 안의 버튼 하나로 끝낼 수 없고, 신청 → 승인 → 회수 → 재발송의
**상태를 고객이 직접 볼 수 있어야** 문의 전화가 줄어든다.

## 7. 관리자 (Phase 6)

**비개발자 운영자 기준**으로 만든다. 화면에 전문용어를 쓰지 않는다 (`slug` → "사이트 주소").

### 운영 핵심

| 화면 | 비고 |
| --- | --- |
| 로그인 | |
| 대시보드 | 오늘 주문 · 재고 부족 알림 |
| 상품 목록 / 등록·수정 | SKU(사이즈×컬러), **실측표 입력**, 이미지, **상품정보제공고시 9항목** |
| 재고 관리 | SKU 단위 |
| 주문 목록 / 주문 상세 | 상태 변경, 송장 입력 |
| **교환·반품 처리** | 승인 → 회수 → 재발송. 별도 화면 필요 |
| 회원 목록 / 상세 | |

### 콘텐츠

공지사항 관리 · FAQ 관리 · 배너/메인 구성

### 시스템

| 화면 | 비고 |
| --- | --- |
| 관리자 계정·권한 | 최고관리자 / 일반관리자. **마지막 최고관리자 보호**, 스스로 잠그기 방지 |
| 통계 | **사이즈별 판매량** — "어느 사이즈를 더 만들지" 판단 근거. 테일러샵에 실질적 가치 |

### 설계 원칙 두 가지

1. **서버 규칙을 저장 전에 알려준다.** 예: "주문된 적 있는 사이즈는 삭제할 수 없고 숨김만 됩니다" 를
   저장 버튼을 누른 뒤가 아니라 **누르기 전에** 보여준다.
2. **개인정보 내보내기**(CSV/xlsx)를 만든다면 기간 필수 · 건수 상한 · 감사 로그 ·
   수식 주입 방지(`=`, `+`, `-`, `@` 로 시작하는 셀)를 함께 넣는다.
