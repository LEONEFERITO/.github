### 가정 A1 — JDK 21 조달 방식 (되돌리기 쉬움, 진행함)

Gradle **toolchain** 으로 JDK 21 을 고정하고 Foojay resolver 로 자동 다운로드한다.

```gradle
java { toolchain { languageVersion = JavaLanguageVersion.of(21) } }
```

- **이유**: ① 확정 스택인 "Java 21" 을 코드로 못박는다 ② 내 PC 의 JDK 17 을 건드리지 않는다
  ③ CI 와 로컬이 **같은** JDK 를 쓴다 (수동 설치는 버전이 갈린다) ④ 설치 작업이 0
- **버린 대안**: 설치된 Temurin 25 사용 — Boot 4.x 가 Java 21~25 를 지원하므로 돌아는 간다.
  하지만 확정 스택이 21 이고, 25 로 개발하면 21 에서만 나는 문제를 못 잡는다.
- **되돌리는 비용**: 한 줄 수정. 언제든 바꿀 수 있다.
- 이 가정이 틀렸다면(예: 사내 표준 JDK 가 따로 있음) 알려주면 바로 교체한다.

## D3. FE 렌더링 — ✅ **확정: Next.js + 정적 내보내기(SSG)**

"React" 라는 확정 조건 안에서의 선택.

| 기준 | A안: React + Vite SPA | B안: Next.js (App Router, SSR/SSG) |
| --- | --- | --- |
| 초기 구축 난이도 | 낮음 — 설정이 단순하고 빠르다 | 중간 — 서버/클라이언트 경계 학습 필요 |
| 월 비용 | **정적 호스팅**(S3+CloudFront) — 거의 무료 | **Node 런타임 상주 필요** → 서버비 ↑ |
| 운영 부담 | 작음 — 빌드 산출물만 올린다 | 중간 — Node 프로세스를 하나 더 관리 |
| 확장성 | CDN 이 다 받아준다 | ISR·서버 캐시 등 도구가 많다 |
| 나중에 바꾸는 비용 | A→B: **큼** (라우팅·데이터 페칭 전면 재작성) | B→A: 큼 |
| **SEO / 상품 SEO** | ⚠️ **기본적으로 안 됨** — 아래 필수 보완책 | ✅ 기본 제공 |
| 카톡·인스타 공유 미리보기 | ⚠️ 안 됨 (OG 태그가 비어서 나감) | ✅ 됨 |
| 학습 가치 (백엔드 개발자 기준) | BE/FE 경계가 명확해 이해하기 쉽다 | React 서버 컴포넌트까지 익힐 수 있다 |

### A안을 고를 경우 — 반드시 포함해야 하는 보완책

커머스에서 **상품 페이지가 검색에 안 잡히고 공유 미리보기가 안 뜨는 건 치명적**이다.
빈 `<div id="root">` 만 있는 HTML 이 크롤러·카톡 봇에 전달되기 때문. 아래 중 하나를 Phase 3 범위에 넣는다.

- **A-1) 엣지에서 메타 주입** — CloudFront Function/Lambda@Edge 가 상품 URL 요청을 보고
  `title`/`description`/`og:image` 를 HTML 에 끼워 넣는다. (비용 저렴, 구현 중간)
- **A-2) 빌드 시 상품별 프리렌더** — 빌드 때 상품 목록을 받아 상품마다 정적 HTML 생성.
  상품 수가 적고(수십 개) 자주 안 바뀌면 가장 단순. **B-1(상품 수) 답에 따라 가능/불가.**
- **A-3) 크롤러 분기 렌더링** — 봇에만 렌더링된 HTML 제공. **비추천** (클로킹으로 오인될 위험).

> 내 견해: **상품 수가 적고 시즌 단위로 교체**되면 A + A-2 가 비용·난이도 모두 낫다.
> 상품이 수시로 바뀌거나 수백 개면 B(Next.js)가 결국 싸다.
> 다만 B 는 **Node 서버가 상주**해야 해서 고객이 내는 월 서버비가 올라간다 — 이게 이 프로젝트의 제약이다.
> **`docs/CLIENT_QUESTIONS.md` B-1(상품 수) 답이 오면 판단이 쉬워진다. 지금 고르기 어렵다면 D3 만 미뤄도 BE 작업은 진행 가능하다.**

## D4. DB — ✅ **확정: PostgreSQL 18**

| 기준 | A안: PostgreSQL | B안: MySQL 8 |
| --- | --- | --- |
| 초기 구축 난이도 | 동일 (Docker 한 줄) | 동일 |
| 월 비용 | 동일 (같은 인스턴스에서 구동) | 동일 |
| 운영 부담 | 중간 | 중간 — 국내 자료·운영 경험자가 더 많다 |
| 확장성 | 동일 수준 | 동일 수준 |
| 나중에 바꾸는 비용 | **큼** — 마이그레이션 SQL·방언 전면 수정 | 큼 |
| 이 프로젝트에 유리한 점 | **JSONB** — 실측표처럼 카테고리별로 항목이 다른 데이터에 강함<br>제약조건·트랜잭션 DDL 이 견고 | 국내 호스팅·인력 생태계가 넓음<br>익숙한 사람이 많음 |
| 주의 | — | JSON 타입이 PG 만큼 강하지 않다 |

> 내 견해: **A(PostgreSQL) 권장.** 이유는 B-4 실측표다.
> 카테고리마다 측정 항목이 다르므로(자켓=어깨·가슴·소매 / 팬츠=허리·허벅지·밑단) 고정 컬럼으로 못 짠다.
> CLAUDE.md 도 "고정 컬럼이 아니라 구조화된 행" 이라고 못박았는데, 이때 PG 의 JSONB + 부분 인덱스가 확실히 편하다.
> **단, 이미 MySQL 운영 경험이 훨씬 많다면 B 도 합리적이다 — 익숙한 DB 가 장애 때 더 빨리 복구된다.**

## D5. Spring Boot 버전 — ✅ **확정: 4.1.1** · CLAUDE.md 작성 시점 대비 상황이 바뀜

> ⚠️ **중요**: CLAUDE.md 의 "3.5.x (생태계 안정)" 은 **더 이상 유효하지 않다.**
> **Spring Boot 3.5.x 의 무료(OSS) 지원은 2026-06-30 에 종료**되었다 (3개월 전).
> 지금 3.5.x 로 시작하면 **첫날부터 무료 보안 패치를 못 받는 상태**다.
> 실 고객 프로젝트이고 유지보수 예산이 없으므로, 이 항목은 A/B 의 무게가 같지 않다.

| 버전 | 출시 | 무료(OSS) 지원 종료 | 상용 지원 종료 | 최신 패치 |
| --- | --- | --- | --- | --- |
| **4.1** | 2026-06-30 | **2027-07-31** ✅ | 2028-07-31 | 4.1.1 |
| 4.0 | 2025-11-30 | 2026-12-31 (⚠️ 3개월 남음) | 2027-12-31 | 4.0.8 |
| 3.5 | 2025-05-31 | **2026-06-30 (종료됨)** ❌ | 2032-06-30 (유료) | 3.5.16 |

| 무료 보안 패치 | ✅ 2027-07-31 까지 | ❌ **없음** (이미 종료) |

> 내 견해: **A(4.1.x) 강력 권장.**
> ① 새 프로젝트라 "3.x 의 안정성" 이 주는 이점(마이그레이션 회피)이 애초에 없다

> ③ Boot 4.x 가 Java 21 을 요구하는데 확정 스택이 정확히 Java 21 이다
> ④ 나중에 올리려면 Jackson 3 전환 비용을 그때 내야 한다. 지금 내면 0원이다
>
> **감수할 것**: 국내 예제가 3.x 기준이라 검색한 코드를 그대로 붙이면 안 맞을 때가 있다.
> 이건 학습 모드 설명으로 내가 메운다 (4.x 에서 달라진 부분을 그때그때 짚는다).
> 4.0 은 무료 지원이 3개월밖에 안 남아 중간 선택지로서 의미가 없다.

## D6. AWS 구성 — **보류 (Phase 7, 고객 답변 필요)**

`docs/CLIENT_QUESTIONS.md` **G-3**(월 비용 허용 범위·예상 트래픽) 답이 기준.
아래 비용은 서울 리전(ap-northeast-2) 대략치이며 **Phase 7 착수 시 실제 요금으로 재산정**한다.

| 기준 | A안: Lightsail 1대 + Docker Compose + Caddy | B안: EC2 + RDS + S3/CloudFront |
| --- | --- | --- |
| 초기 구축 난이도 | 낮음 — 인스턴스 1개, 요금 고정 | 높음 — VPC·보안그룹·RDS·CDN 각각 구성 |
| 월 비용 (대략) | **서버 1만~2만원대** (고정 요금제) | **RDS 만으로 2만~4만원+**, EC2·CloudFront 별도 |
| 운영 부담 | 내가 다 본다 (DB 백업도 직접) | RDS 가 백업·패치를 대신한다 |
| 확장성 | 수직 확장만 (인스턴스 등급 올리기) | 수평 확장·읽기 복제본 가능 |
| 나중에 바꾸는 비용 | A→B: 중간 (DB 덤프 이전) | — |
| DB 장애 시 | **내 책임** — 복구 절차를 내가 갖고 있어야 함 | 자동 백업·특정 시점 복구 |
| 고객 부담 관점 | 저렴함이 최대 강점 | 예측 가능성·안정성이 강점 |

> 참고: 고객이 서버비를 내므로 A 가 유리해 보이지만, **DB 백업 실패 = 주문 데이터 소실**이다.
> A 를 고르면 자동 백업 스크립트 + 복구 리허설을 Phase 7 범위에 반드시 넣는다.
