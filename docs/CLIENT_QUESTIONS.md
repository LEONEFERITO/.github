## A. 판매 방식 — 가장 먼저 답이 필요한 항목

### A-1. 사이트에서 결제까지 하는가?
선택지: ① 온라인 결제·주문·배송까지 (커머스) / ② 카탈로그 + 문의·매장 방문 유도

- **막히는 것**: 프로젝트 규모 전체. Phase 4(장바구니·주문·결제), Phase 5(회원) 착수 여부.
  ②라면 작업량이 **1/3 ~ 1/4** 로 줄고, ①이라면 결제·정산·CS 흐름이 전부 따라온다.
- `답:`

### A-2. (A-1 이 ① 인 경우) 통신판매업 신고와 PG 계약 상태
- 사업자등록번호 / 통신판매업 신고번호 보유 여부
- PG(포트원, 토스페이먼츠, KG이니시스 등) 계약 진행 상태
- 에스크로(구매안전서비스) 가입 여부 — 선결제 쇼핑몰은 법적으로 필요할 수 있다

- **막히는 것**: 결제 연동 착수 시점. **계약 전에는 테스트 키로만 개발하고 운영 전환은 별도 게이트.**
  신고번호 없이 오픈하면 전자상거래법 위반이라 오픈 자체가 막힌다.
- `답:`

### A-3. (A-1 이 ① 인 경우) 배송
- 배송비 정책 (무료 기준 금액? 지역별 추가? 도서산간?)
- 택배사 (CJ대한통운 / 한진 / 우체국 …) 및 송장번호 입력 방식 (수동 / API)
- 제작 리드타임이 있는 상품이 있는가 (기성복이라도 재고 없을 때 몇 주?)

- **막히는 것**: 주문 금액 계산 로직(서버 계산이라 정책이 코드에 들어간다), 배송 상태 화면.
- `답:`

## B. 상품 — LEONEFERITO 의 핵심

### B-1. 상품 수와 운영 단위
- 오픈 시점 상품 수 (대략 몇 개?)
- 시즌(SS/FW) 단위로 교체하는가, 상시 판매인가
- 카테고리 구성 (자켓 / 팬츠 / 셋업 / 셔츠 / 코트 / 액세서리 …)

- **막히는 것**: 목록 페이지 페이지네이션 방식, 카테고리·컬렉션 테이블 설계, 관리자 화면 복잡도.
- `답:`

### B-2. 한 상품의 옵션 구조
- 사이즈 × 컬러 조합만인가, **핏(운동체형/일반체형)도 선택 옵션**인가?
  - (a) 핏은 상품의 성격 — "이 상품은 운동체형 전용" (상품 속성)
  - (b) 핏은 고객이 고르는 옵션 — 같은 스타일에 두 가지 패턴 (SKU 축)
- 옵션 조합별로 가격이 다른 경우가 있는가 (예: 빅사이즈 추가금)

- **막히는 것**: **SKU 설계 자체.** (a)면 `Product.fitType`, (b)면 SKU 축이 3개(사이즈×컬러×핏).
  나중에 바꾸면 재고·주문 데이터 마이그레이션이 필요하다 — 여기서 확정해야 한다.
- `답:`

### B-3. 사이즈 체계
- 표기 방식: 44/55/66 여성식? S/M/L/XL? 정장 호수(95/100/105)? 팬츠 인치(28~38)?
- 상의와 하의가 다른 체계를 쓰는가
- **핏별로 같은 라벨이 다른 실측인가** (예: 운동체형 100 ≠ 일반체형 100)

- **막히는 것**: 사이즈 마스터 데이터, 사이즈 가이드 페이지, 필터 UI.
- `답:`

### B-4. 상품별 실측표 제공 가능 여부 — **이 사이트의 핵심**
- 사이즈별 실측치를 상품마다 제공할 수 있는가? (어깨/가슴/허리/총장/소매/허벅지/밑단 등)
- 측정 기준은 통일되어 있는가 (평평히 놓고 단면? 둘레?)
- 오차 허용범위를 표기할 것인가 (예: ±1cm)

- **막히는 것**: 실측표 데이터 구조(Phase 2), 상품 상세의 최우선 영역.
  **이게 없으면 LEONEFERITO 는 일반 쇼핑몰과 차별점이 없다.**
- `답:`

### B-5. 모델 착용 정보
- 상품 사진 모델의 키·몸무게·착용 사이즈를 공개할 수 있는가
- 가능하면 체형 설명도 (예: "가슴 105 / 허리 80 / 운동 5년")

- **막히는 것**: 상품 상세의 모델 정보 영역. 없으면 그 영역을 비운다.
- `답:`

### B-6. 상품정보제공고시(의류) 필수 항목 — 법적 의무
아래는 전자상거래 고시상 **텍스트로 제공해야** 하는 항목이다 (이미지로만 넣으면 안 됨).
상품마다 채울 수 있는지, 아니면 공통 기본값을 쓸지 확인 필요.

- [ ] 제품 소재 (혼용률까지)
- [ ] 색상
- [ ] 치수
- [ ] 제조자 / 수입자
- [ ] 제조국
- [ ] 세탁방법 및 취급 시 주의사항
- [ ] 제조연월
- [ ] 품질보증기준
- [ ] A/S 책임자와 연락처

- **막히는 것**: Phase 2 상품 엔티티 필드. 미입력 상품을 노출 허용할지 여부(권장: 차단).

## C. 회원 · 인증

### C-1. 회원 가입이 필요한가
- 비회원 주문을 허용하는가 (허용 시 주문 조회는 주문번호+연락처로)
- 회원 혜택이 있는가 (등급, 적립금, 쿠폰) — 있으면 Phase 5 범위가 커진다

- **막히는 것**: Phase 5 전체, 주문 테이블의 회원 연결 방식.
- `답:`

### C-2. 간편 로그인
- 카카오 / 네이버 / 구글 / Apple 중 필요한 것
- 각 플랫폼 개발자 앱 등록은 **고객사 명의**로 할 수 있는가 (심사에 사업자 정보 필요)

- **막히는 것**: OAuth 연동 작업. 앱 등록 없이는 개발도 못 한다.
- `답:`

### C-3. 개인정보
- 개인정보처리방침 문안을 제공받을 수 있는가 (법무 검토된 것)
- 개인정보 보호책임자 이름·연락처
- 수집 항목 최소화 동의 — 생년월일·성별을 꼭 받아야 하는가?

- **막히는 것**: 가입/주문 폼 필드, 약관 페이지. 방침 없이 오픈하면 위법.
- `답:`

## D. 교환 · 반품 — 의류에서 가장 흔한 CS

### D-1. 정책
- 교환·반품 신청 가능 기간 (수령 후 며칠)
- 배송비 부담 (단순변심 시 왕복? 사이즈 교환 1회 무료?)
- 교환 불가 조건 (착용 흔적, 택 제거, 세탁, 수선)
- 맞춤 수선을 거친 상품은 교환 불가인가

- **막히는 것**: Phase 4 교환 흐름 상태 전이도, 정책 안내 페이지, 관리자 승인 화면.
  **의류는 사이즈 교환이 CS 의 대부분** — 이 흐름은 부가 기능이 아니라 핵심이다.
- `답:`

### D-2. 처리 주체
- 교환 신청을 관리자가 **승인**하는가, 자동 접수인가
- 회수 택배는 누가 부르는가 (고객 / 고객사)

- **막히는 것**: 상태 전이 단계 수. 자동이면 단순, 승인이면 관리자 화면이 필요.
- `답:`

## G. 운영 · 인프라

### G-1. 도메인
- 보유한 도메인이 있는가 / 희망 도메인
- 네임서버 변경 권한을 누가 갖는가
- THE MANLY 와 LEONEFERITO 는 별도 도메인인가, 서브도메인인가

- **막히는 것**: Phase 7 HTTPS 발급, SEO 설정.
- `답:`

### G-2. AWS 계정 주체 — **고객이 서버비를 내므로 중요**
- AWS 계정을 **고객사 명의**로 만들 수 있는가 (권장)
  - 권장 이유: 서버비가 고객사 카드로 직접 결제되고, 계약 종료 후에도 자산이 고객에게 남는다.
- 결제 카드 등록 주체
- 내가 운영 접근 권한(IAM)을 받는 범위

- **막히는 것**: Phase 7 전체. 내 계정으로 만들면 나중에 이관 작업이 따로 필요하다.
- `답:`

### G-3. 월 서버 비용 허용 범위
- 월 얼마까지 감당 가능한가 (예: 3만 / 5만 / 10만원)
- 예상 트래픽 (일 방문자 수 감 — 100명? 1,000명?)

- **막히는 것**: D6(AWS 구성) 선택. 비용 상한이 구성을 결정한다.
- `답:`

### G-4. 운영자
- 상품 등록 / 배너 교체 / 주문 처리를 **누가** 하는가
- 그 사람의 기술 수준 (비개발자 가정하고 만들 예정)
- 동시에 여러 명이 관리자를 쓰는가 (권한 분리 필요?)

- **막히는 것**: Phase 6 관리자 화면 설계. 전문용어 없는 UI 를 만들어야 한다.
- `답:`

### G-5. 이메일 발송
- 주문 확인 / 배송 안내 메일을 보내는가
- 발신 이메일 주소 (도메인 메일? Gmail?)
- 알림톡(카카오)을 쓰는가 — 별도 계약 필요

- **막히는 것**: 주문 완료 후 알림 흐름. 없으면 관리자가 수동으로 연락.

## H. 두 사이트의 관계 (LEONEFERITO ↔ THE MANLY)

### H-1. 연결 방식
- 회원 계정을 공유하는가
- 장바구니·주문 데이터를 공유하는가
- 관리자를 하나로 쓰는가
- 도메인: 완전 분리 / 서브도메인 / 링크만

- **막히는 것**: **D2(저장소·서버 구조).** 지금 정하면 Phase 1 구조에 반영되고,
  나중에 바꾸면 인증·DB 스키마를 건드려야 한다.
- `답:`

### H-2. THE MANLY 사이트 범위 (후순위 — Phase 8)
- 방문 예약 기능이 필요한가 (예약 시간 슬롯, 중복 방지)
- 비포/애프터 갤러리 — 고객 초상권 동의는 받아뒀는가
- 후원 선수 소개

- **막히는 것**: Phase 8. LEONEFERITO 오픈 후 별도 Phase 0 으로 다시 확인.
- `답:`
